# 审查、发布、部署与验收

## 发布负责人检查

发布任务使用准确版本、Build（项目使用时）、源码完整 SHA、PR、CI run/job、产物
digest、目标环境、依赖版本和负责人。版本/Build 在冻结候选时分配，多仓产品需要明确
版本矩阵。不要改写已发布 tag、同名镜像或旧 Build 来掩盖不同源码。

| 门禁 | 所需证据 | 负责人动作 |
| --- | --- | --- |
| 实现 | 验收逐项对应、候选 SHA、Draft PR、风险 | 完成候选与交付说明 |
| 审查 | 当前 SHA 的正式审查结论、遗留问题 | 决定是否可合并 |
| 指定验证 | 精确 SHA 的 CI/数据库/性能/契约结果 | 处理 FAIL/UNKNOWN/NOT_RUN |
| 合并 | 授权、真实 merge SHA、主线检查 | 按授权合并并更新跟踪 |
| 产物/Release | source/image 对应、manifest/digest、版本说明 | 核验独立发布授权 |
| 部署 | 环境授权、实际运行版本、迁移与回滚证据 | 核验运行身份和健康状态 |
| 启用 | 具体功能开关/权限及独立启用授权 | 按范围开启并核对真实状态 |
| 真实验收 | 原清单每项与真实用户/客户端证据 | 确认全范围后才完成源任务 |

已编译不能替代镜像安全、数据库演练、性能或真实客户端门禁。产物上传成功应回读远端
digest 和源码 revision；部署成功应回读实际运行身份。默认关闭的功能即使部署了代码，
仍未启用。维护、资金、身份、CDKEY、凭据和跨系统写入路径按项目特定门禁处理，不能
从本模板取得额外生产授权。未知外部投递/交易状态先对账，不盲目重试。

## 审核候选与交接

交接包至少包含：准确 Issue/Linear/PR、原验收逐项表、源码/构建/镜像身份、实际验证
环境与结果、未执行项、部署/启用授权边界、数据库迁移/回滚、运行回读步骤、后续负责人。
交接只是输入，负责人仍要独立审查。叶任务不得替父交付签收。

文档、模板或流程工具的任务按其自身范围验收；不用给不存在的产品强造部署门禁。
但公开分支、Draft PR、默认分支已合并和正式 Release 是不同事实，分别说明。

## 对用户的更新说明

面向普通用户，陈述模块版本、实际变化、已知限制和阶段。不要公开内部主机、数据库、
CI 原始日志、私有工单或账号标识。测试候选明确标为候选，预计日期标注“暂定”。

可采用：

> 组件 A 1.2.0 候选已完成开发，正在验证客户端兼容性。本次更新改善分页加载，正式
> 版本时间暂定，待验证通过后另行通知。当前公开版本维持 1.1.0。

发布后把新问题关联到真实版本/源码/环境，查重再建 Issue，按缺陷范围独立分支修复。
既有验收保持可追溯，新回归不能用历史绿灯覆盖。

## 完成投影

原负责人按全部验收完成 GitHub 源 Issue 与 Linear 后，发当前正文绑定的 accepted
回执，含 owner_receipt_url 与 acceptance 证据。协调器核验既有 CLOSED/Done 后投影
Project 完成；不能通过 CI、PR 合并或某个子任务的 accepted 推动父交付 Done。
