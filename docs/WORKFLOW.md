# 开发、审查与更新流程

## 任务开始

核对真实仓库与 applicable AGENTS、干净/脏状态、当前 SHA 和已有任务。恢复聊天时先读
原需求、源 Issue、原分支与最新证据，避免重复实现、重复派工或覆盖已有工作。
日常问答无需工程工单；功能、缺陷、配置与交付文档适用本流程。

Issue 至少写：问题/目标、包含与排除范围、可逐项判断的验收条件、依赖、验证环境、
负责人、下一步。先查重。将 Issue 加入自己的跨项目 Project，设置项目、优先级、
工作类型；尚未检查的验证层级用待核验。不要把计划写成完成事实。

Linear 的 native 与 linked 方式见 ONBOARDING.md。查找用准确源 Issue URL；标题只可
找候选，attachment URL 和 UUID 才建立身份。不能在原生镜像之外另建一个重复任务。

## 实施

使用独立分支或 worktree，保留共享 checkout 脏改动。建议分支
`codex/eng-123-gh-45-pagination-fix`；未取得 Linear 号可先 `codex/gh-45-pagination-fix`。
开始时发 development 进度，明确全部范围还是叶实现范围。每个提交引用
`Refs example-org/service-api#45`。记录完整 commit SHA，不能仅写分支或短 SHA。

及时建立 Draft PR。PR 说明当前行为、修改结果、验收清单、验证证据、风险、回滚和
未完成的交付步骤。链接准确 Issue 和 Linear；公开 PR 避免私有跟踪链接，准确关联在
私有系统保留。需部署/启用/真实验收的 Issue 使用 Refs，避免用自动关闭关键词替代验收。

## 审查

Draft PR 是开发阶段。实现完成且证据齐备、正式请求审查时，取消 Draft 并按授权将
任务置 review/待审核。审核者检查当前准确 SHA、需求与验收匹配、危险写入路径、
兼容性、测试范围、失败/未运行项和交付风险；不能只看绿灯。

审查通过后使用 merge_pending/待合并，实际合并需明确授权。合并后记录 merge SHA；
head SHA、merge SHA、构建 SHA 不一致时解释关系，并在最终构建源码上重验必要门禁。
变更了实现就重新确认受影响审查和检查；不得沿用旧 SHA 的认可。

## 验证

按 Issue 原验收逐条记录：PASS、FAIL、UNKNOWN、NOT_RUN、SKIP 与原因。静态/本地、
指定 CI/数据库、跨系统真实契约、部署、配置启用、真实用户/客户端验收独立记录。
测试模拟通过只证明模拟覆盖范围。CI 失败不能标通过；HTTP 200、网页保存成功也不能
代替实际功能验收。文档任务可按其文档范围验收，不因此宣称产品功能已经交付。

## 跨仓库协调

以协调 Issue 保存共同目标、接口/版本矩阵和最终验收；每个仓库有自己的实施 Issue、
Linear、分支与 PR。用显式 URL 和真实 blocks/blocked-by 连接。只有实际先决条件才
标阻塞；“有关联”不等于“阻塞”。各工作线只报告自身范围，由主负责人集中判断整体。
若用户授权并行，可开独立工作窗口；不得让多个写入者同时维护相同平台状态。

例如 API 和客户端各通过单测，但两端契约尚未共同验证：两项代码可报告候选完成，
父集成 Issue 仍待验证。部分进度可以写普通事实评论，不能伪造 `scope=issue` 的全范围回执。

## 即时回写与完成

开始、提交/推送、Draft PR、正式审核、CI 结果、阻塞、交付或下一步改变时回写源
Issue、PR、Project 和 Linear。新事实用唯一 event_id；重试同一事件复用相同 ID 和
相同 payload。正文/状态变化则重读、重新计划，不能硬覆盖。

全部验收条件满足、负责人确认且相应授权已执行，才按原流程关闭 GitHub Issue、完成
Linear。随后 accepted 回执只投影既有事实。协调器不替人创建完成，不自动关闭父任务。
部署、发布与更新说明见 RELEASE.md。
